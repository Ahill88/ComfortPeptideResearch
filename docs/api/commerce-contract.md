## 1. Email (port + outbox) -- `apps/api/src/email/email.types.ts`
`EmailService.enqueue({ to, template, data, dedupeKey? })` inserts an EmailOutbox row (idempotent on dedupeKey) and returns immediately; a worker sends
via the configured provider with retries and backoff. Templates (data keys): `email_verification {link, name?}`, `password_reset {link}`,
`order_confirmation {orderId, totalCents, currency}`, `order_shipped {orderId, carrier, trackingNumber, trackingUrl|null}`. Links are built from env `STOREFRONT_PUBLIC_URL`
(`/verify-email?token=...`, `/reset-password?token=...`). Providers via env `EMAIL_PROVIDER`: `console` (dev/test default: writes to the outbox and logs a redacted line, never the token text outside dev) and `resend` (HTTP API by `fetch`, key from `EMAIL_API_KEY`, sender `EMAIL_FROM`). Tokens appear only inside the email body, never in logs outside `console` mode in development/test.

## 2. Customer accounts (API) -- base `/v1/auth`
Session = opaque 32-byte base64url token in an httpOnly cookie `hf_session` (SameSite=Lax, Secure unless development/test, Path=/, Max-Age 30 days absolute, 7 days idle), only SHA-256 stored (CustomerSession). Browsers send it with `credentials: 'include'` (CORS: allow-listed origin + `Access-Control-Allow-Credentials: true`). State-changing requests that carry the cookie must also send an allow-listed `Origin` (CSRF defence). The existing single identity resolver (`apps/api/src/wallet/customer-identity.ts`, used by wallet, checkout, orders) accepts: the dev/test `x-customer-email` header (unchanged) OR a valid session cookie (any runtime). In production-like runtimes ONLY the cookie works.
- `POST /auth/register {email, password, name?}` -> 202 `{message:'Check your email to verify your account.'}` identical for new and existing emails (no enumeration); password policy >= 12 chars <= 256; sends `email_verification` (token valid 24h, single use). Never reveals whether the email exists. An existing Customer row created by an order is attached to the credentials ONLY when the token is confirmed.
- `POST /auth/email-verification/confirm {token}` -> 204 (marks emailVerifiedAt, consumes the token) | 400 generic `Invalid or expired link.`
- `POST /auth/login {email, password, totp?}` -> 200 `{customer:{id,email,name|null,emailVerified:true,mfaEnabled:boolean}}` + Set-Cookie; every failure 401 `{message:'Invalid sign-in.'}` (unknown email, wrong password, locked, wrong code) and constant-ish timing (always run scrypt). After a CORRECT password only: unverified email -> 403 `{code:'EMAIL_NOT_VERIFIED', message:'Verify your email first.'}`; MFA enabled and no totp -> 401 `{code:'MFA_REQUIRED', message:'Enter your authentication code.'}`. Lockout 5 failures / 15 min. scrypt + TOTP + AES-GCM seed storage exactly like admin auth (reuse `apps/api/src/admin/auth/credentials.ts`; key env `CUSTOMER_MFA_ENCRYPTION_KEY` >= 32 chars; unset -> MFA enrol 503, login for non-MFA customers still works).
- `POST /auth/logout` -> 204 (revokes the session, clears the cookie). `GET /auth/session` -> 200 `{customer:{...}}` | 401.
- `POST /auth/password-reset/request {email}` -> 202 generic; `POST /auth/password-reset/confirm {token, newPassword}` -> 204 (revokes ALL sessions) | 400 generic.
- `POST /auth/mfa/enroll` (session) -> 201 `{otpauthUri, seedBase32}`; `POST /auth/mfa/enroll/confirm {code}` -> 204; `POST /auth/mfa/disable {password, code}` -> 204.
- `GET /auth/profile` -> `{id,email,name|null,emailVerified,mfaEnabled}`; `PATCH /auth/profile {name}` -> 200; `GET /auth/addresses` -> `{items:[Address]}`; `POST /auth/addresses`, `PATCH /auth/addresses/:id`, `DELETE /auth/addresses/:id` (204); Address = `{id,label|null,recipient,line1,line2|null,city,region,postalCode,country,isDefault}` (<= 20 per customer; exactly one default).
- The old 503 stubs in `apps/api/src/auth` are replaced; `apps/api/src/auth/auth-startup.check.ts` no longer blocks production boot once these exist (the failing spec test `production startup requires server-backed email verification, password reset, and MFA` in tests/authentication-eligibility.test.ts must pass honestly: read it).

## 3. Totals, stock and orders
- `Order.totalCents = subtotalCents + shippingCents + taxCents` (integer cents). Shipping: env `SHIPPING_FLAT_CENTS` (default 0), `SHIPPING_FREE_OVER_CENTS` (default unset = never free). Tax: env `TAX_RATE_BPS` (basis points, default 0 = none; documented as a flat placeholder, NOT a tax engine). Both rounded half-up, Int32 safe.
- `POST /v1/orders/quote {items:[{productId, lotCode, quantity}]}` (public, rate limited) -> 200 `{currency:'USD', subtotalCents, shippingCents, taxCents, totalCents, lines:[{productId, lotCode, quantity, unitCents, lineCents}], unavailable:[{productId, reason:'out_of_stock'|'inactive'|'unknown_lot', available:number|null}]}`.
- `POST /v1/orders` (existing) now: computes the same totals, reserves stock atomically (`UPDATE "Product" SET inventory = inventory - q WHERE id=$1 AND inventory >= q`; ledger rows ORDER_RESERVE with orderId; all lines in the order's transaction) or fails 409 `{code:'OUT_OF_STOCK', message:'Insufficient stock for <name>.', productId, available}`; sets `expiresAt = now + ORDER_HOLD_MINUTES` (env, default 60); response gains `subtotalCents, shippingCents, taxCents`. Identity: in dev/test an anonymous body `email` is still accepted (existing tests); in production-like runtimes a session is required and the order belongs to the session's customer (body email ignored/must match).
- Release: `InventoryService.releaseForOrder(tx, orderId, reason)` (interface in `apps/api/src/commerce/inventory.types.ts`) puts every reserved quantity back (ORDER_RELEASE rows, unique per (order, product, kind)) and sets `Order.inventoryReleasedAt`; idempotent. Called when: an unpaid order passes `expiresAt` (a scheduled sweep cancels it, ONLY if no purchase CryptoTransaction is PREPARED-unexpired/SUBMITTED/FINALIZED for it), the admin cancels a PENDING_PAYMENT order, or a PAID/PROCESSING order is refunded before shipping.
- Admin inventory (`/v1/admin`, session guard): `GET /admin/inventory?q=&lowStockOnly=&limit=25&cursor=` -> `{items:[{productId,sku,name,active,onHand:number,reserved:number (held by unpaid unexpired orders),lowStockThreshold:number|null,lowStock:boolean}], nextCursor}`; `POST /admin/inventory/:productId/adjust {delta:int !=0 |delta|<=100000, reason:1-200}` (STAFF ok; result may not go below 0) -> 200 item; `GET /admin/inventory/:productId/ledger?limit=50&cursor=` -> `{items:[{id,delta,kind,reason|null,orderId|null,adminName|null,createdAt}], nextCursor}`; `POST /admin/inventory/:productId/threshold {lowStockThreshold:int>=0|null}` (OWNER). Audit actions `inventory.adjust`, `inventory.threshold`.

## 4. Customer orders (API) -- identity per section 2
- `GET /v1/orders?limit=20&cursor=` (mine, newest first) -> `{items:[{id,status,totalCents,subtotalCents|null,shippingCents,taxCents,currency,createdAt,itemCount,carrier|null,trackingNumber|null}], nextCursor}`
- `GET /v1/orders/:id` (mine; 404 for anyone else's) -> `{id,status,totalCents,subtotalCents|null,shippingCents,taxCents,currency,createdAt,shippingAddress|null,items:[{productId,slug,name,lotCode,quantity,unitCents}],shipments:[{carrier,trackingNumber,trackingUrl|null,shippedAt,deliveredAt|null}],timeline:[{status,at}]}`. `timeline` has ONLY customer-safe status changes (no staff notes, no admin names). `trackingUrl` is built server-side from carrier+number for USPS/UPS/FedEx/DHL (null for OTHER).
- When an admin ships an order the API enqueues `order_shipped` (dedupeKey `order_shipped:<orderId>:<trackingNumber>`); paying enqueues `order_confirmation`.

## 5. Refunds / cancel after payment -- admin (OWNER)
`AdminOrderDetail` (docs/api/admin-orders.md) gains `refund: null | {id, status:'REQUESTED'|'SUBMITTED'|'FINALIZED'|'FAILED', amountAtomic:string, txSignature:string|null, requestedAt:ISO, failureReason:string|null}` and `allowedActions` gains `'refund'` (PAID and PROCESSING orders with no refund in progress). Endpoints (each returns the updated AdminOrderDetail):
`POST /admin/orders/:id/refund {reason:1-500}` (creates the refund request through the existing refunds service; the order stays PAID/PROCESSING until the refund finalizes) ; `POST /admin/orders/:id/refund/submit {}` (signs and broadcasts through the bound MERCHANT_SIGNER; 503 `Refund signing is not available.` when none is bound); `POST /admin/orders/:id/refund/verify {}` (re-reads the chain; on FINALIZED the order becomes REFUNDED and unshipped stock is released). A SHIPPED/DELIVERED order cannot be refunded here (409). The refund destination is ALWAYS the customer's own linked wallet (existing refunds rule), never admin-supplied.

## 6. Sanctions screening
Public OFAC SDN list "Digital Currency Address" entries are ingested into SanctionsAddress (job at startup + every `SANCTIONS_REFRESH_HOURS`, default 24; source URL env `SANCTIONS_LIST_URL`, default the Treasury SDN export the engineer verifies). The default `ComplianceScreen` (apps/api/src/wallet/transfers/compliance-screen.ts, token COMPLIANCE_SCREEN) becomes this screen: a listed address is refused at wallet link, on-ramp, transfer destination and checkout prepare with 403 `{message:'This wallet cannot be used.'}` and an audit event; matching is exact on the address string. Rule when the list has never loaded: development/test fail OPEN with a warning; any other runtime fails CLOSED (503 `Compliance screening is not ready.`). Admin: `GET /admin/compliance/sanctions` -> `{source, lastRun:{fetchedAt,entryCount,status,error|null}|null, addressCount}`; `POST /admin/compliance/sanctions/refresh` (OWNER) -> 200 same shape | 503. This supports, and is not, a compliance programme: say so in docs.

## 7. Network info (public) -- mainnet readiness
`GET /v1/public/network-info` -> `{network:'solana-devnet'|'solana-mainnet', usdcMint:string, explorerTxBase:string (e.g. 'https://explorer.solana.com/tx/'), explorerClusterQuery:string ('?cluster=devnet' or ''), livePayments:boolean}`. The storefront refuses to build or sign a payment whose network/mint differs from this.
